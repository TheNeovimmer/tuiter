1. INTRODUCTION                                      *tuiter-introduction*

tuiter is a Postman/Insomnia-style API explorer that lives in your editor.
Write requests in `.http` files, send them with one key, read responses in
floating windows — with a request sidebar, collection runner, history,
environments, dynamic variables, and JSON pretty-printing. Pure Lua, no
plugin dependencies (requests go out via `curl` over |vim.system()|).

==============================================================================
2. REQUIREMENTS                                      *tuiter-requirements*

- Neovim >= 0.10 (uses vim.system, window titles, vim.json)
- `curl` on PATH

Install with lazy.nvim / LazyVim: >
  {
    "TheNeovimmer/tuiter",
    branch = "main",
    dependencies = {}, -- zero plugin dependencies: pure Lua + curl only
    cmd = { "Tuiter", "TuiterRun", "TuiterRunAll", "TuiterSaveBody",
            "TuiterHistory", "TuiterEnv", "TuiterResponse", "TuiterCopyAs" },
    ft = { "http", "graphql" },
    opts = {},
  }
<
The plugin lazy-loads: `cmd` triggers on any Tuiter* command, `ft` on
opening a .http / .graphql file.
==============================================================================
3. USAGE                                                *tuiter-usage*

Open a `.http` file and press `<leader>il` for the request sidebar, or put
the cursor on a request and hit `<leader>is`.

See `examples/demo.http` for a runnable demo: most requests hit a public
API; the local ones need `python3 tests/server.py` running.

==============================================================================
4. REQUEST FILE FORMAT                            *tuiter-request-format*

REST Client style, many requests per file:

- `### Name` starts a new request (optional name); a bare `METHOD URL` line
  also starts one without a name
- First line: `METHOD URL` — GET is implied when the method is omitted
- `Header: value` lines until the first blank line
- After the blank line, everything until the next `###` is the body
- `#` lines are comments; `# @name foo` names the request
- `# @skip` excludes a request from run-all / CI (destructive or flaky
  requests) — the request still sends normally with <leader>is
- `@name = value` lines define request-scoped variables (use as `{{name}}`)

Example: >
  ### Auth
  # @name login
  @token = abc123
  POST https://api.example.com/login
  Authorization: Bearer {{token}}
  Content-Type: application/json

  {"user": "ada"}
<

==============================================================================
5. KEYMAPS                                            *tuiter-keymaps*

Buffer-local, in `.http` files, under the `<leader>i` group (free in
LazyVim; shown as a "tuiter" which-key group):

  <leader>is   Send request under cursor
  <CR>         Send request under cursor (Insomnia/REST Client muscle memory)
  <leader>il   Request sidebar
  <leader>ia   Run all requests in the file (summary)
  <leader>ic   Cancel in-flight requests
  <leader>ik   Keymap help float
  <leader>ih   Request history (pick & re-run)
  <leader>ie   Select environment
  <leader>ir   Toggle response window
  ]r / [r      Next / previous request
  gx           Open the request URL in the browser (vars resolved)

All keymaps are configurable via |tuiter-config|: set a key to false to
skip it, or `keymaps = false` to disable all of them.

In insert mode, `<C-x><C-o>` completes `{{var}}` placeholders (request
vars, env vars, dynamic values).

==============================================================================
6. REQUEST SIDEBAR                                  *tuiter-sidebar*

`<leader>il` or `:Tuiter` opens a Postman-style list of every request in
the file: ★ favorites first, then color-coded methods (GET green, POST
blue, PUT/PATCH yellow, DELETE red), name, URL, and the last response
status as a `[200]`/`[404]` mark. A hint bar shows the keys.

  <CR>   Run request (sidebar stays open — response opens to its right)
  g      Jump to the request in the file
  *      Toggle favorite (persisted)
  /      Filter requests by name/URL/method (Insomnia-style search)
  e      Switch environment (sidebar re-renders)
  a      Run all requests
  c      Copy as curl
  ?      Keymap help
  q      Close

Composer: in `.http` files, request lines are highlighted like Insomnia's
composer — color-coded methods, blue URLs, section titles (`###`), and
@vars.

==============================================================================
7. COLLECTION RUNNER                              *tuiter-run-all*

`<leader>ia` or `:TuiterRunAll` runs every request in the buffer
sequentially (150ms apart) and opens a summary float: ✓ green / ✗ red
lines with method, name, status, time, size (⏭ grey lines for `# @skip`
requests, which are never sent). `<CR>` on a line jumps to that request
in the file. Run-all does not pollute history.

Every send (single run or run-all) also stamps the request line in the
`.http` file with inline virtual text — `✓ 200 · 45ms` / `✗ 404 · 12ms` —
so the buffer itself shows the last result. While a request is in flight
the line shows `↻ running…`; the mark is replaced by the result when the
response lands.

==============================================================================
8. RESPONSE WINDOW                                *tuiter-response*

Insomnia-style: a tab bar (Body | Headers | Timeline) over the response,
with a status bar showing `tuiter · METHOD URL · HTTP 200 OK · 123ms ·
1.2KB · env: dev` — green when ok, red on error/4xx-5xx. The tab bar
shows HTTP status · time · size on the right.

Failures are never silent: DNS/connection/timeout/cancel errors fire a
warning toast, and the status bar + Body tab show the curl error instead
of an empty body (the request line gets a `✗ error` mark).

  1/2/3  Body / Headers / Timeline tab
  t      Cycle tabs
  q      Close response
  p      Toggle pretty / raw JSON body
  y      Copy current tab (body, headers, or timeline)
  c      Copy as curl (shell-safe, Insomnia-style)
  f      Save body to a file (:TuiterSaveBody)
  z      Zoom: response fills the screen (tab bar hidden)
  r      Resend the request
  ?      Keymap help

- Body tab: JSON is pretty-printed, treesitter-highlighted and foldable
  (zc/zo); HTML/XML/CSS/JS bodies get their filetype syntax too
- Headers tab: response headers with keys highlighted
- Timeline tab: per-phase timings — DNS lookup, TCP connect, TLS
  handshake, request sent, waiting (TTFB), download, total — plus size,
  redirects, protocol and content type

9. DYNAMIC VARIABLES                              *tuiter-dynamic*

Placeholders `{{name}}` are resolved at send time in order: request vars →
env vars → shell env → dynamic values. Unresolved names stay visible.

  {{$timestamp}}      Unix seconds
  {{$uuid}}           Random v4 UUID (lowercase)
  {{$guid}}           Random v4 UUID (uppercase)
  {{$randomInt}}      Random integer 0–10^6
  {{$status}}         Status code of the last response
  {{$body.a.b.0.c}}   Dotted path into the last response's JSON body
                      (array indexes are 0-based, like Insomnia)

Example — use a token from a login response: >
  POST https://api.example.com/login
  Content-Type: application/json

  {"user": "ada"}

  GET https://api.example.com/me
  Authorization: Bearer {{$body.token}}
<

Responses from single runs feed `{{$body.*}}`; the collection runner also
records each response, so later requests can chain off earlier ones.

==============================================================================
10. COMMANDS                                          *tuiter-commands*

  :Tuiter                Toggle request sidebar
  :TuiterRun [lnum]      Send request under cursor
  :TuiterRunAll          Run all requests, show summary
  :TuiterCancel          Cancel in-flight requests
  :TuiterSaveBody        Save last response body to a file
  :TuiterHistory         Pick a past request and re-run it
  :TuiterEnv             Select environment
  :TuiterResponse        Toggle response window
  :TuiterCopyAs [lang]   Copy snippet for the request under the cursor
                         (curl|python|js|ts|go|rust|php|graphql; no arg = picker)
  :TuiterStream          Stream the request under the cursor (SSE, `# @stream`)
  :TuiterWatch [sec]     Re-run the request under the cursor every N seconds;
                         run again to stop (healthcheck)
  :TuiterJUnit [path]    Export the last run-all results as JUnit XML
                         (default tuiter-junit.xml)
  :TuiterCI              Run all requests headlessly, write JUnit, exit
                         non-zero on any failure (CI)
  :TuiterScaffold        Open a scaffolded .http buffer
  :TuiterFormat          Pretty-print the JSON body under the cursor
  :TuiterImportPostman   Convert a Postman collection JSON to a .http buffer
  :TuiterImportOpenapi   Convert an OpenAPI spec JSON to a .http buffer
  :TuiterImportCurl      Paste a curl command (DevTools / docs / `gh api -i`)
                         and convert it to a .http buffer

Pro features, see README for the full guide: named request chaining
({{login.body.token}}), assertions (`# @test status == 200`), OAuth2/bearer
auth (`# @auth oauth2 token_url=.. client_id=.. client_secret=..` — a 401
auto-refreshes via the refresh grant whenever a refresh_token is
available), streaming, pagination (`# @paginate`), .env support (hot-
reloaded on disk changes), per-request `# @delay`, and secret redaction
in history. In .http buffers `K` previews the resolved value of a {{var}}
and `gd` jumps to its definition in the env file.

==============================================================================
10a. GRAPHQL FILES                                     *tuiter-graphql*

`.graphql`/`.gql` buffers get the same keymaps. The endpoint comes from a
`# @url` directive; each query/mutation/subscription operation becomes a POST
with JSON body `{"query": ..., "variables": <# @variables or null>}`.
`# @variables` applies to the next operation and supports `{{var}}`:
>
  # @url http://localhost:4000/graphql
  # @variables {"userId": "{{$body.user.id}}"}

  query GetUser($id: ID!) {
    user(id: $id) { name }
  }
<
==============================================================================
10b. FORM BODIES & COOKIES                             *tuiter-forms*

- `multipart/form-data` + body of `key=value` lines -> curl `-F` fields
  (file uploads: `key=@path`; relative paths resolve against the request
  file's directory and `{{vars}}` inside them are substituted). Raw
  `--boundary` bodies are sent as-is.
- `application/x-www-form-urlencoded` + body of `key=value` lines (no `&`)
  -> curl `--data-urlencode` fields (values encoded for you).
- `curl.cookie_jar = true` (default) keeps a per-project jar under
  `stdpath("data")/tuiter/cookies/`, so login cookies persist across
  requests. Disable with `curl = { cookie_jar = false }`.

==============================================================================
10c. DIAGNOSTICS                                     *tuiter-diagnostics*

While editing a `.http` file, tuiter validates the buffer and shows
LSP-style warnings: a bare method without URL, URLs without http(s)://,
header/body mistakes. Refreshes on write and on edit.

==============================================================================
11. STATUSLINE INTEGRATION                        *tuiter-statusline*

`require("tuiter").statusline()` returns `env: dev · HTTP 200` for the
current environment and last response. With lualine: >
  { "tuiter.statusline", cond = function()
      return require("tuiter").statusline() ~= ""
    end }
<

==============================================================================
12. CONFIGURATION                                    *tuiter-config*

>  {
    opts = {
      keymaps = { -- false disables that key; keymaps = false disables all
        run = "<leader>is", list = "<leader>il", run_all = "<leader>ia",
        cancel = "<leader>ic", help = "<leader>ik",
        history = "<leader>ih", env = "<leader>ie", response = "<leader>ir",
        browser = "gx", -- open request URL in browser (vim.ui.open)
      },
      curl = { timeout = 30, insecure = false, max_redirects = 8,
             cookie_jar = true, compressed = true },
      env_files = { "http-client.env.json", "tuiter.env.json" },
      default_env = "default",
      run_all = { concurrency = 1, delay = 150 }, -- parallel runner
      windows = { width = 120, max_height = 40, sidebar_width = 62 }, -- floats
    },
  }
<

`opts.windows` sizes the response float (width / max_height) and the
request sidebar (sidebar_width).
Example — move everything off <leader>i: `opts = { keymaps = { run =
"<leader>xr", list = "<leader>xl", cancel = false } }`.

15. HIGHLIGHT GROUPS                            *tuiter-highlights*

Customize with |:highlight| (all `default = true`, so your colorscheme
wins when it defines them):

  TuiterGet/Put/Patch/Delete  method colors (GET green, POST blue,
                              PUT/PATCH yellow, DELETE red)
  TuiterOk / TuiterError      status marks and summary rows
  TuiterUrl                   request URLs in .http files
  TuiterSection               `###` section titles
  TuiterVar                   `@name = value` variables
  TuiterStar                  ★ favorite marks
  TuiterHeaderKey             header names in the Headers tab
  TuiterStatusOk/Err          response status bar background
  TuiterStatusHint            sidebar hint bar

==============================================================================
15. DEVELOPMENT                                    *tuiter-development*

  make test    # headless unit tests + integration test against a local server
  make format  # stylua

- Requests go out via curl over vim.system — never blocks the editor
- The parser is pure Lua (no vim.*), so it runs in plain headless tests
- Everything is lazy-loaded: the module chain loads only when you use a
  Tuiter* command or open a `.http` file
- History: stdpath("data")/tuiter/history.json
- Favorites: stdpath("data")/tuiter/favorites.json

==============================================================================
16. HEALTH CHECK                                    *tuiter-health*

`:checkhealth tuiter` verifies Neovim >= 0.10, `curl` on PATH, and that
the data + cookie-jar directories under `stdpath("data")/tuiter` are
writable (history, favorites, oauth cache and cookies are persisted
there). Also notes when `jq` is missing (the `J` filter in the response
window needs it).
